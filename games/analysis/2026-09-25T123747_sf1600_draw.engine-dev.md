## 2. Diagnosis — root causes that cost the most

1. **No PST / development / king-safety term (v1 only).** Explains the entire 1.a3…9.g4 pawn-shuffle opening (ply 1–27) and pawn-structure misses like ply 51. **Already fixed by v2's tapered PeSTO PSTs** — not actionable further from this game.
2. **Search-depth ceiling from missing TT, killer/history ordering, null-move pruning and PVS/LMR.** Plain alpha-beta with MVV-LVA-only ordering re-explores the same subtrees on every iterative-deepening pass and every sibling at every node, capping effective depth well short of what the ~331cp/477cp swings at ply 117–129 needed to see. This is the single biggest lever for both middlegame (ply 37, 47) and endgame (ply 117, 119, 129) losses. **Already queued (items 2, 4, 5, 6)** — this game is strong evidence to keep them at the top.
3. **No passed-pawn / king-safety / long-endgame technique term in eval.** Ply 69 (missing c7) is a clean example, and the cluster of 6 flagged mistakes across plies 143–189 shows the engine has no compass once it's down material in a long ending — it just makes locally-plausible but strategically empty moves. **Already queued (item 7, mop-up/passed pawns/king safety)**, and this game's very long tail (117–203, 8 of 14 flagged mistakes) argues for prioritizing the *passed-pawn* half of that item specifically, since that's what's concretely evidenced here.

## 3. Improvement plan (ordered by expected Elo gain per hour)

1. **Transposition table + hash-move ordering** (already queued #2). `engine/src/main.rs`: `Search` already computes a Zobrist hash every node (`hash(pos)`, reused from repetition detection) — trivial to key a `HashMap<u64, TtEntry>` (or a fixed-size array of `TtEntry { key, depth, score, flag, best_move }` to avoid hashmap overhead) off the same value. Probe at the top of `negamax` before move generation; store on exit; try the TT move first in the ordering loop before MVV-LVA. This is the single highest-leverage change available — every mistake in the blunder table above ply 37 is at least partly a "didn't see far enough" problem. Effort: ~2-3h. Expect **+60-120 Elo** at this level (baseline currently has *no* move-ordering memory across iterations or siblings). Test: A/B gauntlet (`arena.gauntlet bin/destroyer bin/destroyer-v3`), 50+ games; also log nodes/sec and depth-reached on the ply-47 and ply-117 FENs before/after.

2. **Killer moves + history heuristic** (already queued #4). `engine/src/main.rs::negamax`: keep two killer moves per ply (`[[Option<Move>; 2]; MAX_PLY]`) and a `history[from][to]` (or `[role][to]`) table incremented on beta cutoffs; sort quiet (non-capture) moves by history score after captures/TT-move/killers. Directly targets the "quiet move ordering is arbitrary" gap visible at ply 37 (Bd3 vs Bc4 — a quiet developing move) and ply 143-189 (quiet king/knight endgame moves). Effort: ~1-2h. Expect **+30-60 Elo**, compounds with TT. Test: same gauntlet; check that beta-cutoff rate on quiet nodes improves.

3. **NEW — aspiration windows around the previous iteration's score.** `engine/src/main.rs::best_move`: currently every depth re-searches the root with a full `(-INF, -alpha)` window from scratch. Once depth ≥ 4, start with a narrow window `(prev_score - 25, prev_score + 25)` (in cp) and only fall back to a full-width re-search on fail-low/fail-high. Cheap, synergizes directly with the TT (item 1) since a re-search hits mostly-cached nodes. Not currently queued anywhere. Effort: ~30-45 min. Expect **+10-20 Elo** (mostly an extra half-ply of depth in the 5s budget, which matters most on the ply-117/119/129-style tactical misses). Test: nodes-to-reach-depth-N before/after on a fixed suite of mid-game FENs from this game; gauntlet to confirm no regression from failed-window overhead.

4. **Passed-pawn term in eval** (already queued #7, splitting out the concrete part this game evidences). `engine/src/eval.rs::evaluate`: add a per-side passed-pawn bonus scaled by rank-from-promotion and by `eg_phase` (e.g. `[0,5,10,20,35,60,100,0]` cp table indexed by distance to promotion, mirrored for black), computed in the same board-iteration loop that already builds `mg`/`eg` (need one bitboard test per pawn: no enemy pawn on the same or adjacent file ahead of it — shakmaty's `Board::by_role`/`by_color` bitboards make this a handful of `Bitboard` intersections, no extra move generation needed). This is exactly what would have flagged c7 over Bxc4 at ply 69. Effort: ~1-1.5h. Expect **+30-50 Elo**. Test: unit test asserting `evaluate()` prefers the ply-69 FEN's `c7` over `Bxc4`; gauntlet.

5. **Check extensions + quiescence bad-capture (SEE) pruning + `score mate N`** (already queued #3). `engine/src/main.rs::negamax`: `let ext = if pos.is_check() && ply < CHECK_EXT_CAP { 1 } else { 0 };` add to `depth` for the recursive call, capped (e.g. total extensions ≤ 8 per line via a counter threaded through, or cap by `ply`) so it can't blow the 5s budget on one line. Pair with a simple SEE (or the existing MVV-LVA sign as a cheap proxy: skip captures where `victim_value - attacker_value < -100` in `quiesce`, `engine/src/main.rs:143-147`, unless in check). Also switch the `info` print (`main.rs:182`) to emit `score mate N` when `alpha.abs() > MATE - MAX_PLY`. Directly targets the ply-129 mate-score swing and the forced-mate stretch around plies 118-140. Effort: ~1-1.5h. Expect **+20-40 Elo**, plus a correctness/UCI-hygiene fix (mate scores currently print as absurd raw `cp` values, e.g. `score cp 9989`). Test: unit test on a known mate-in-N FEN checking `info` output; gauntlet.

6. **Null-move pruning** (already queued #5) and **PVS + LMR** (already queued #6). `engine/src/main.rs::negamax`: null-move (`R=2-3`, skip when in check or in pawn-only endgames to avoid zugzwang errors — relevant here since several of the flagged endgame plies, e.g. 117-189, are exactly the low-material positions where naive null-move is unsound) frees up depth cheaply; PVS (search the first move full-width, subsequent moves with a null window `(-alpha-1, -alpha)` and re-search on fail-high) plus LMR (reduce depth by 1-2 for late, quiet, non-check moves) both reduce effective branching factor once TT + move ordering (items 1-2) exist to make re-searches cheap. Effort: ~2-3h combined. Expect **+40-70 Elo** combined, but rank below items 1-4 since the payoff is smaller until TT/ordering are in place. Test: gauntlet; confirm null-move is disabled in the zugzwang-prone king+pawn/king+minor endings like plies 117-203 of this game (add a regression test using this game's late-endgame FENs).

7. **NEW — small correctness nit found while reviewing `quiesce` for this game's long, repetition-heavy tail:** `engine/src/main.rs::quiesce`, the stalemate branch (`if moves.is_empty() { return if in_check { -MATE + ply } else { 0 }; }`) returns a hardcoded `0` instead of `self.draw_score(ply)`, unlike the equivalent branch in `negamax`. Inconsistent with the contempt logic added in v3 — a stalemate reached via a capture sequence inside quiescence currently ignores contempt. Low Elo impact (~0-5) but a one-line fix (`self.draw_score(ply)`), worth doing opportunistically alongside item 5 since you'll already be touching this function.

8. **Opening book** (already queued #1). Still worth having for reliability/variety, but this game shows its urgency has dropped since v2's PSTs already fix the catastrophic 1.a3…9.g4 shuffle that originally motivated it — rank it last for Elo/hour purposes now. Effort: ~1-2h to generate + wire up 10-ply-deep Stockfish-generated white lines. Expect **+10-20 Elo** (mainly variance reduction / avoiding book-less inaccuracies in the first few moves, not a repeat of this specific game's opening problem).

9. **NEW — mobility term in eval** (not currently queued; lower-ranked because of a real implementation risk, see Risks). `engine/src/eval.rs::evaluate`: a small per-piece mobility bonus (count of attacked squares, not full legal moves, to stay cheap — e.g. `piece.attacks(occupied) & !own_pieces` popcount, weighted ~2-4cp for minors, ~1-2cp for rooks/queen, tapered) would generalize beyond static PSTs and reduce placement mistakes like ply 37's Bd3-vs-Bc4. Effort: ~1h. Expect **+15-30 Elo** *if* implemented as O(1) bitboard popcounts — see Risks. Rank this after TT/killers/passed-pawns since its value is smaller and its performance risk is real.

## 4. Risks

- **Check extensions (item 5) need a hard depth/ply cap wired into `negamax` itself**, not just `quiesce`. Today only `quiesce` enforces `MAX_PLY` (`main.rs:127`); `negamax`'s recursion currently always terminates because `depth` strictly decreases every call. Once extensions can add back depth, an unbounded or loosely-bounded check-extension chain could recurse past `MAX_PLY` (96), which both wastes the 5s budget on one line (starving other root moves — the existing `nodes & 2047` deadline check still caps wall-clock time, so the 5s rule itself is safe, but search *quality* collapses) and could index `self.path` out of range in `is_repetition`/`self.path.truncate(...)` if `ply` ever exceeds what `path`'s capacity assumes. Add an explicit ply cap identical in spirit to `quiesce`'s before shipping item 5.
- **Mobility (item 9) must not call full legal-move generation inside `evaluate()`.** `evaluate()` is called on every node (including every quiescence stand-pat check), so anything more expensive than O(1) bitboard ops there will directly cut nodes/sec and effective search depth — undermining the TT/killer/null-move gains from items 1, 2 and 6. Use attack-bitboard popcounts, not `pos.legal_moves()`, and benchmark nodes/sec before/after on a fixed 5s search to confirm no regression.
- **Null-move pruning (item 6) is unsound in low-material/zugzwang positions** — several of this game's own flagged endgame plies (117-203, minor-piece and king endings) are exactly the case where a null-move heuristic can return a false fail-high and miss the best move. Disable null-move when non-pawn material is below a threshold (or simply when the side to move has no pieces besides king+pawns).
- **`score mate N` (item 5) is a UCI-output correctness fix, not just cosmetic:** any downstream tooling (or a future non-python-chess harness) that expects a `score mate N` token when near-mate could otherwise misinterpret `score cp 9989` as a genuine (and wildly wrong) evaluation; low risk today since `arena/play.py` tolerates raw cp via `mate_score=10_000`, but worth fixing before this engine is ever run under a different UCI client.
- None of the above changes the 5s/move contract: TT/killer/history/aspiration windows only affect *what* is searched within the existing node-count deadline check (`nodes & 2047 == 0 && Instant::now() >= deadline`), which remains the sole time-safety mechanism and is untouched by every item in this plan.
