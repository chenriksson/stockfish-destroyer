## 2. Diagnosis

**(a) Mate conversion — not a problem in this game, but fragile by construction.**
The first mate score in the depth-18 trace appears at ply 50: after 25...e4 SF evaluates the position (from Black's perspective) at −9997, i.e. **mate in 3** (moves) for White. We then played 26.Qxh4+ Kg7 27.Qe5+ Kf8 28.Qhe7# — exactly 3 moves, the theoretical minimum. So conversion was optimal here.

But this is luck of a simple mating net (lone king, two attackers, few legal replies), not evidence the search generally finds mates efficiently. With `MAX_PLY 96`, no TT, and **no `score mate N` reporting** (confirmed: `best_move` only ever prints `info depth {d} score cp {alpha}`, never a mate score), the engine:
- can't distinguish "mate in 3" from "mate in 30" in its own output (no mate-distance pruning, so it won't stop early or prefer the faster mate when a slower one is also winning — negamax's `>=beta`/`alpha.max` never special-cases `MATE`-range scores),
- re-derives the whole PV from scratch every iterative-deepening depth (no TT/hash move), so against a king with real escape squares and defenders, the mating net could take meaningfully longer to find at depth, costing search depth budget elsewhere in the 5s window.
This risk is real for higher-Elo games where SF will contest king safety rather than hang a knight into a forced mate. Already queued (item 3: check extensions + quiescence bad-capture pruning + `score mate N`) — this game doesn't change that priority, just confirms it hasn't bitten us *yet*.

**(b) Time management — correct, not a bottleneck.**
`think_time()` is fed `go movetime 5000` by `arena/play.py` (python-chess's `Limit(time=5.0)` is translated to a `movetime` UCI command, so the `wtime`/`btime`/`winc` branch of `think_time` is dead code in this competition format — worth knowing so nobody spends time tuning it). The engine budgets `min(ms,5000) - 100`ms = 4900ms, a sane fixed 100ms IPC/process margin. `best_move`'s iterative-deepening loop is safe: `self.stopped` set inside `negamax`/`quiesce` is rechecked *before* using an in-progress depth's `depth_best`, so a partially-searched depth is always discarded and the previous complete depth's best move is kept — no risk of returning a corrupted/incomplete-depth move. Root moves are re-ordered (best-first) between iterations, which is good practice (cheap substitute for a hash move) even without a TT. Net: nothing to fix here; not a source of the Elo gap.

**(c) What actually caps strength against a non-blundering opponent:**
1. **No transposition table.** Every iterative-deepening depth restarts from zero shared knowledge; transpositions (very common after move-order-independent development, e.g. this game's 1.Nf3/2.g3/3.d4 vs 1.d4/2.Nf3/2.g3) are re-searched from scratch. This is almost certainly the single biggest depth (and therefore Elo) tax in the engine right now. Already queued (#2).
2. **Move ordering is MVV-LVA-only.** Non-capturing moves in the main search have zero ordering signal (`mvv_lva` returns 0 for any non-promotion quiet move, so alpha-beta gets no pruning benefit from move order in quiet positions — which is most positions outside forcing sequences). No killer moves, no history heuristic. Already queued (#4), but note it's high leverage *specifically because* quiet-move ordering today is uniformly random (insertion order from `legal_moves()`).
3. **No pruning beyond plain alpha-beta + quiescence.** No null-move, no LMR, no PVS (`negamax` always searches every move with a full `[-beta,-alpha]` window, `best_move`'s root loop does re-narrow alpha but children never get a null-window probe). Already queued (#5, #6). This is the second-biggest depth tax after the TT.
4. **Evaluation is PST-only material.** `eval.rs` has tapered PeSTO material+PST and nothing else: no mobility, no bishop pair, no pawn structure (isolated/doubled/passed), no king safety. This is not on the current queue except via "mop-up/passed pawns/king safety" (item 7), which is narrower than what's below — see plan item 6 (**new**).
5. **Per-node `Chess::clone()` instead of make/unmake.** `child = pos.clone(); child.play_unchecked(&m)` allocates/copies a full board for every move at every node in both `negamax` and `quiesce`. This is a plain nodes/sec tax that will make every future search feature (TT, null-move, LMR — all queued) less effective per second of think time than they could be. Not urgent to rewrite (shakmaty's `Chess` doesn't expose a cheap unmake, so this is a real refactor), but worth a 10-minute profiling check before investing multiple hours in search features, so the team knows whether nodes/sec or algorithmic pruning is the binding constraint.

## 3. Improvement plan (ranked by expected Elo/hour)

1. **Transposition table + hash-move ordering** *(already queued, #2)* — highest leverage item on the board.
   - Implement: fixed-size array of entries `{key: u64, depth: u8, score: i32, bound: Exact|Lower|Upper, best: Option<Move>}`, indexed by `hash(pos) % table_size` (reuse the existing `hash()` in `main.rs`), replace-if-deeper-or-equal.
   - Where: new `engine/src/tt.rs`; probe at the top of `Search::negamax` before move generation (return immediately on a sufficient-depth exact/bound hit); store at the end of the move loop; use the stored move as the first move tried in the ordering `sort_by_key` in both `negamax` and `best_move`'s root loop.
   - Elo: **+80 to +150**.
   - Test: `uv run python -m arena.gauntlet bin/destroyer bin/destroyer-tt` (A/B vs current build); confirm `info depth N` is reached at equal-or-greater depth for the same think time on a few fixed test positions; add a unit test that two transposed move orders into the same position produce the same TT hit.

2. **Killer moves + history heuristic** *(already queued, #4)*.
   - Implement: `killers: [[Option<Move>; 2]; MAX_PLY as usize]` (two per ply) and `history: [[i32; 64]; 64]` (from×to), updated only on quiet-move beta cutoffs in `Search::negamax`.
   - Where: `main.rs` `Search` struct + `negamax`'s move-ordering `sort_by_key` (today quiet moves all score `0` from `mvv_lva`, so this is pure signal where there is currently none).
   - Elo: **+30 to +60**.
   - Test: gauntlet vs previous tag; sanity-check nodes-to-reach-depth-N drops on a quiet middlegame test position (not just tactical ones, where MVV-LVA already does fine).

3. **Null-move pruning** *(already queued, #5)*.
   - Implement: in `negamax`, when `depth >= 3`, not in check, not at the root, and non-pawn material remains (guard against zugzwang), try a null move (`pos.clone()` with side to move flipped, no move played) at `depth - 1 - R` (R=2); if the resulting score `>= beta`, cut off.
   - Where: `Search::negamax`, before the main move loop.
   - Elo: **+40 to +80**.
   - Test: gauntlet; add a regression test with a known zugzwang FEN (K+P endgame) confirming null-move is disabled/doesn't misplay when only kings+pawns remain.

4. **PVS + LMR, plus aspiration windows** *(PVS/LMR already queued, #6; aspiration windows is new and rides on the same code path)*.
   - Implement PVS: search the first (TT/killer-ordered) move with the full `(-beta,-alpha)` window, subsequent moves with a null window `(-alpha-1,-alpha)`, re-searching full-width on fail-high. Implement LMR: reduce depth by 1-2 for quiet, non-check, late move-list moves (index > ~3) at `depth >= 3`. Implement aspiration windows in `best_move`: seed each new depth's `alpha`/`beta` from the previous depth's score ± ~25cp, re-searching with a wider window on fail-low/high instead of always using `(-INF, INF)`.
   - Where: `Search::negamax` (PVS/LMR), `Search::best_move` (aspiration windows, replacing the current always-full-width `-INF..INF` per depth).
   - Elo: **+50 to +100** (PVS+LMR) **+10 to +20** (aspiration windows, cheap once the TT exists).
   - Test: gauntlet; verify PVS/LMR don't change the chosen best move on a small fixed-depth tactics suite (they should only change speed, not the final answer, modulo search instability which should be checked for).

5. **Check extensions + quiescence bad-capture pruning + `score mate N`** *(already queued, #3)*.
   - Implement: extend search depth by 1 when `pos.is_check()` at the start of a `negamax` node (cap total extensions per line, e.g. +2, to avoid runaway depth in perpetual-check lines); in `Search::quiesce`, skip clearly-losing captures (SEE < 0, or as a cheap first pass, skip captures where `mvv_lva` victim value < attacker value and no PV/pin context); emit `info depth {d} score mate {n}` from `best_move` whenever `alpha.abs() >= MATE - MAX_PLY`, with `n = (MATE - alpha.abs() + 1) / 2` signed by which side mates.
   - Where: `Search::negamax` (extension), `Search::quiesce` (pruning), `Search::best_move`'s `println!` (mate reporting).
   - Elo: **+20 to +40**. (This game shows conversion is *currently* fine, but only because the mating net was trivial — see Diagnosis 2a; this closes that gap before it costs a game.)
   - Test: a small suite of mate-in-3/5/7 FENs — confirm correct `score mate N` and that the engine finds the shortest mate within 5s once one exists; gauntlet for overall Elo.

6. **Evaluation: mobility + bishop pair + basic pawn structure** *(new — not covered by the current queue, which only has king-safety/passed-pawns/mop-up)*.
   - Implement: (a) bishop-pair bonus (+30mg/+40eg when a side holds both bishops — trivial, count `Role::Bishop` per side in the existing material loop); (b) doubled-pawn penalty (-10 to -15cp per extra pawn sharing a file) and isolated-pawn penalty (-10 to -15cp for a pawn with no friendly pawn on an adjacent file) computed once from `pos.board()`'s pawn bitboard per file; (c) simple mobility (count of legal destination squares per non-pawn piece, ~2-4cp each for knight/bishop, ~1-2cp for rook/queen).
   - Where: `engine/src/eval.rs::evaluate()`, alongside the existing material/PST loop.
   - Elo: **+20 to +40**.
   - Test: new `eval.rs` unit tests (two bishops beats bishop+knight at equal material; isolated-pawn position scores worse than the same material without); gauntlet.

7. **King safety (pawn shield) + passed pawns + mop-up eval** *(already queued, #7)*.
   - Where: `engine/src/eval.rs::evaluate()`.
   - Elo: **+20 to +50** — likely *larger* at SF1800-2000 than lower levels, since that's where the opponent actually keeps its king safe and pushes passed pawns instead of blundering (per the game facts: our current avg loss is already ~1cp/move here, so the remaining gap to beat higher Elo is exactly in these structural terms, not tactics).
   - Test: gauntlet specifically weighted at SF1800/2000 rather than the lower rungs.

8. **Opening book** *(already queued, #1)*.
   - Implement: pre-generate ~10-ply-deep White lines with full-strength Stockfish, store as `(zobrist_hash -> Vec<move>)`; in `main()`'s `Some("go")` arm, check the book before invoking `Search::best_move` and play a (randomized-among-top) book move directly if the current position hashes into it.
   - Where: new `engine/src/book.rs` + a generated data file; `main.rs`'s `go` handler.
   - Elo: **+10 to +30** — lowest of the list: this game's opening (moves 1-10) already loses only ~1-3cp/move on average, so a book mainly buys consistency and saved think-time rather than fixing a real weakness.
   - Test: gauntlet; verify all book moves are legal from their stored hash and that transposed move orders still hit the book.

## 4. Risks

- **UCI `stop` is not handled at all.** `main()`'s command match has no `Some("stop")` arm — it falls into the `_ => {}` no-op. Because the engine is single-threaded and `best_move()` blocks synchronously for up to ~4.9s, a `stop` (or `isready`, or `quit`) sent *during* a search sits unread in stdin until the current search returns on its own deadline, then gets silently discarded (`stop`/extra `isready` have no handler) or processed late (`quit`). `arena/play.py`'s python-chess `SimpleEngine.play()` with a fixed `movetime` never sends `stop` mid-search in the current harness, so this hasn't bitten us — but it means the engine cannot be interrupted early by anything, and any future harness/GUI/`--abort-hopeless`-style change that relies on `stop` will silently misbehave (delayed-not-immediate bestmove) rather than error loudly.
- **No watchdog independent of the node-counted deadline check.** The only clock check is `if self.nodes & 2047 == 0 && Instant::now() >= self.deadline`. If a future change (e.g. a buggy extension) creates a code path with very few nodes-per-real-time (or an infinite loop that doesn't call `negamax`/`quiesce`), the 5s/move rule could be silently violated with no external way to recover short of killing the process — worth a cheap defense-in-depth (e.g., also check elapsed time once per root move in `best_move`, independent of the node counter) before adding null-move/LMR/check-extensions, since those are exactly the kind of change that can accidentally blow up node cost per unit search progress.
- **`go` argument handling defaults anything without `movetime`/`wtime` to 5000ms**, including `go infinite` or `go depth N`. Not exercised by `arena/play.py` today (always sends `movetime`), but if any analysis/test tooling drives the engine directly via `go depth N` expecting a depth-limited (not time-limited) search, results will be silently wrong (time-limited instead) rather than erroring.
- **None of the queued search features (TT, null-move, LMR, check extensions) risk the 5s rule by themselves** as long as the existing `self.nodes & 2047 == 0` deadline check remains inside every recursive function that can be called many times without returning (this includes any new node type — e.g. a null-move recursive call must also increment `self.nodes` and hit the same check). Flag this explicitly during implementation review of each queued item.
- **Adding a TT introduces a new correctness risk class**: hash collisions and stale entries around draw/repetition scoring. Since `draw_score` depends on `ply` (root-relative) and `contempt` (root-decided, not stored in the position), a naive TT keyed only on Zobrist hash + depth will return incorrect scores for repetition/draw nodes if reused across different root contempt values or ply offsets. When implementing TT (queued #2), exclude or special-case draw-score nodes, or store contempt/ply-independent scores only.
