# Engine-Dev Analysis — 2026-09-25T124045_sf1800_win (WIN vs SF 1800, white, checkmate in 105 plies)

Engine that played: **Destroyer 0.3.0 / engine-v2** (commit `2c0be6e`). Current tree is **0.4.0 / engine-v3**,
which is identical in search/eval to v2 plus repetition/50-move/insufficient-material detection and 30cp
contempt (already done, per prompt). All findings below are about the search/eval code that is unchanged
between the two, so they apply directly to what's currently in `engine/src/main.rs` and `engine/src/eval.rs`.

## 0. Depth/NPS measurement (new data point for this game)

Ran the current binary once on the position right before move 18 (`r6r/2qbkp2/2p2bpp/1pn1p3/4P3/1BP1NN2/PPQ2PPP/3R1RK1 w - - 2 18`,
taken from this game) with `go movetime 5000` on this (≈2x slower than the Apple M5 Pro that played the game) machine:

```

info depth 3 score cp 152 nodes 18083

info depth 6 score cp 96  nodes 5235941

```

Depth 6 was the last **completed** iteration in 5s (depth 7 was started and abandoned when the clock ran out —
`Search::best_move`, `engine/src/main.rs:160-190`, discards an incomplete iteration entirely rather than
keeping any partial improvement). That's **~1.05M nodes/sec** and an effective branching factor of ~3.5-4.2
between iterations (5,235,941-1,259,795 nodes spent on depth 6's own pass vs. 1,259,795-127,865 on depth 5's —
decent for MVV-LVA-only ordering with no TT, but there's nothing pruning the tree beyond plain alpha-beta).
Even doubling raw speed (M5 Pro) doesn't buy a full extra ply against a ~4x-per-ply node-count curve, so
**engine-v2 almost certainly searched only 6, occasionally 7, ply (3-3.5 full moves) for every move of this
game.** That ceiling is the single biggest thing wrong with the current engine and is the common thread behind
nearly everything below.

Raw NPS (~1.05M) is also low for a Rust engine with a `Copy`-friendly board type. Two likely costs per node,
neither incremental: `hash()` (`main.rs:21-23`) recomputes the full Zobrist hash from scratch every node purely
for repetition detection, and `pos.legal_moves()` does full legality filtering (self-check testing) rather than
reusing pin/check info already known from the parent node. Neither is a bug, both are just paid on every single
node — see plan item 8.

## 2. Diagnosis — root causes

1. **Search depth ceiling (~6 ply) from missing TT / pruning / better ordering.** No transposition table, no
   null-move pruning, no PVS/LMR, and move ordering limited to MVV-LVA at every node (`main.rs:36-42`, used in
   both `negamax` and `quiesce`). This directly caused both flagged blunders (each sits exactly where a
   forced/semi-forced tactical sequence of 4-8 plies exceeds the horizon) and is the dominant contributor to the
   16 cp/move background drift across the whole game.
2. **Zero passed-pawn awareness in `evaluate()` (`engine/src/eval.rs:160-181`).** The only per-square term is
   the static PeSTO PST (`EG_PAWN`, `eval.rs:24-33`), which gives a 7th-rank pawn about +13 to +17 — roughly the
   same order of magnitude as a slightly-better-placed knight. The b-pawn reached b7, fully supported, on **move
   31** and wasn't queened until **move 47** (16 moves / 32 plies later, via the 46.Rc8!! sac) — a lot of
   shuffling (Rd3-Rb3-Rc1-Rd1+-Rc1-Rc5+-Rd5+-Rc3-Rc8, the rook visits c1 twice and d-file three times without a
   coherent plan) that gave 1800-strength Stockfish 32 plies of free tries to generate swindle chances. A
   engine that valued "supported pawn one step from queening" anywhere close to its true worth would have looked
   for the promotion breakthrough far sooner.
3. **Checks are not extended, so the search's own "forcing" move choices actively shrink its effective horizon.**
   This is really a special case of #1, but it's worth calling out on its own because it's exactly what produced
   the costlier of the two blunders (23.Qc5+): the engine has no mechanism that recognizes "I just forced a
   near-forced sequence, I should look past it, not stop at my nominal depth."

## 3. Improvement plan (ordered by expected Elo/hour)

1. **Transposition table + hash-move ordering** *(already queued #2)*. Add a `Vec<TTEntry>` (or a fixed-size
   array indexed by `hash & mask`) storing `{key, depth, score, flag: Exact/Lower/Upper, best_move}`. Probe at
   the top of `Search::negamax` (`main.rs:80`) before move generation; on a sufficient-depth hit with the right
   flag, return immediately; otherwise use the stored move to search first (ahead of MVV-LVA) and store on exit
   from every node, including at the root (`Search::best_move`, `main.rs:160-190`, replacing the current
   "retain/insert previous best" hack with a proper TT-driven hash move). Clear the table on `ucinewgame`
   (`main.rs:249-252`). **Est. +150-300 Elo** (this is the item most directly attacking root cause #1). Test:
   rerun the depth-probe FEN above with `go movetime 5000` and confirm it reaches depth 9-11+ instead of 6;
   then `arena.gauntlet` old vs. new, 100+ games.

2. **Null-move pruning** *(already queued #5)*. In `negamax`, when `depth >= 3`, not in check, and the side to
   move has non-pawn material (cheap check: reuse the piece iteration already done in `eval.rs::evaluate` or a
   simpler one-pass count), try a reduced-depth search after a "null" move (side-to-move flips, no board
   change) with a null window; on a beta cutoff, prune. shakmaty's `Chess` doesn't have a built-in null move, so
   build the flipped position via its `Setup`/`from_setup` path (clear `ep_square`, flip `turn`) rather than
   `play_unchecked`. **Guard hard against zugzwang**: skip null-move whenever the side to move has only king +
   pawns — this game's whole second half is exactly that kind of ending, so an unguarded null-move here would
   actively hurt. **Est. +100-150 Elo.** Test: gauntlet vs. current build; additionally hand-verify on 2-3 known
   zugzwang K+P endgame FENs that the guard prevents a bad null-move-induced blunder.

3. **PVS + Late Move Reductions** *(already queued #6)*. `negamax`'s move loop (`main.rs:105-113`) currently
   searches every move with the full `(-beta, -alpha)` window (the root loop in `best_move` already does a
   form of this narrowing, but interior nodes don't). After the first (best-ordered) move, search subsequent
   moves with a null window `(-alpha-1, -alpha)` and a reduced depth for quiet late moves, re-searching full
   width/depth only on fail-high. **Est. +50-100 Elo**, compounds with items 1-2 since a hash move makes "first
   move" ordering trustworthy. Test: gauntlet; also compare nodes-to-depth-N on the probe FEN before/after (want
   fewer nodes for the same depth, not just more depth for the same nodes).

4. **Aspiration windows in iterative deepening** *(NEW)*. `Search::best_move` (`main.rs:163-166`) resets
   `alpha = -INF` at the start of every depth. Instead, after depth 1, start each iteration with a narrow window
   around the previous iteration's score (e.g. ±25-50cp), widening and re-searching on fail-low/fail-high. Small,
   self-contained change (~15-20 lines), no new data structures. **Est. +10-25 Elo** on its own, but the real win
   is a modest (5-15%) node-count reduction that stacks with items 1-3 to buy fractional extra depth for free.
   Test: node count at fixed depth on the probe FEN before/after; gauntlet to confirm no strength loss from a
   too-narrow window causing repeated re-searches.

5. **Check extensions (capped) + quiescence bad-capture (SEE) pruning + `score mate N`** *(already queued #3)*.
   Extend by +1 ply (capped, e.g. max +2 per line via a ply-indexed counter to bound worst case) whenever
   `pos.is_check()` at the top of `negamax` — this is precisely what would have kept 23.Qc5+ off the board (the
   whole point is to stop a self-inflicted check from *shrinking* the effective horizon). In `quiesce`
   (`main.rs:119-158`), add a simple SEE and skip captures that lose material outright (not in check) before
   recursing, cutting a lot of wasted quiescence nodes. Add `score mate N` to the `info` line in `best_move`
   (`main.rs:182`) when `alpha.abs() > MATE - MAX_PLY`. **Est. +30-60 Elo**, plus this is the direct fix for the
   -240 blunder in this game. Test: replay the exact ply-45 position (`r2r4/2qbkp2/2p2bpp/1P1B4/4P3/4p3/PPQ2PPP/3R1RK1 w - - 0 23`)
   through the fixed engine at `movetime 5000` and confirm it no longer prefers Qc5+ over fxe3; gauntlet.

6. **Passed-pawn + basic king-safety (pawn shield) eval terms** *(already queued #7)*. In `eval.rs::evaluate`,
   add a passed-pawn bonus (no enemy pawn on the same or adjacent file ahead of it) scaled steeply by rank —
   Stockfish-style tables give a protected 7th-rank passer several hundred cp, not the ~15 cp our current PST
   gives it. This game is the concrete evidence: the fully-supported b7 pawn sat for 32 plies before the engine
   found the promotion idea. Add a minimal pawn-shield term (missing pawns on the 3 files in front of a
   castled king cost a small penalty) at the same time — cheap, same function. **Est. +40-80 Elo**, and
   independently improves conversion speed against stronger opponents who won't blunder as readily as this 1800
   did. Test: from the move-31 position (b-pawn just reached b7), verify `bestmove` at `movetime 5000` heads
   toward a promotion breakthrough (e.g. prefers `Ra1`/`a4` pawn-race ideas or an immediate rook sac pattern)
   rather than a purely kingside plan; gauntlet.

7. **Killer moves + history heuristic** *(already queued #4)*. Add 2 killer-move slots per ply
   (`[[Option<Move>; 2]; MAX_PLY as usize]` on `Search`) and a `[[i32; 64]; 64]` history table indexed
   `[from][to]`, incremented on quiet-move beta cutoffs (`main.rs:109-111`, `main.rs:152-154`). Order quiet moves
   after captures+hash move by (killer, then history score). **Est. +30-60 Elo**, best realized once null-move/
   PVS give more cutoffs to exploit — do this after items 1-3. Test: gauntlet; sanity-check cutoff rate
   (beta-cutoffs at move-index 0-1) improves vs. baseline on a fixed test suite of middlegame FENs.

8. **Reduce fixed per-node cost: incremental Zobrist hashing** *(NEW)*. `hash()` (`main.rs:21-23`) is called
   once per node in `negamax` (not `quiesce`) purely to feed repetition detection, and recomputes the Zobrist
   key from scratch each time rather than updating it incrementally as the move is made (XOR out moved/captured
   piece, XOR in new square, castling/ep changes). At ~1.05M nps this is a meaningful fixed cost per node. Making
   `Move` carry (or a helper compute) an incremental hash delta would speed up raw search, translating to
   roughly 0.3-0.5 extra ply of depth headroom on top of whatever items 1-3 already buy. **Est. +15-30 Elo**.
   Test: nodes/sec on the probe FEN before/after (want a clear NPS jump with identical bestmove/score at each
   depth); gauntlet.

9. **SEE-based capture ordering in the main search, not just quiescence** *(NEW, small, bundle with item 5)*.
   Once a SEE routine exists for quiescence pruning (item 5), reuse it to order captures in `negamax`'s move
   loop (`mvv_lva`, `main.rs:36-42`) instead of the coarser MVV-LVA-only key — cuts tree size a bit further
   before TT is warmed up. **Est. +5-15 Elo.** Test: node count at fixed depth, gauntlet.

10. **Opening book** *(already queued #1)*. Lower priority than the queue currently implies, based on this
    game: our first ~20 plies lost the least cp of the whole game (avg well under 15 cp/move) even completely
    unaided, so a book buys polish/time-savings, not the Elo the search/eval items above do. Still worth doing
    for consistency, just not before items 1-8. **Est. +10-30 Elo.** Test: gauntlet vs. current build over a
    fixed opening suite.

## 4. Risks

- **Null-move zugzwang (item 2).** This game's entire second half is a long single-minor-piece/rook-and-pawn
  ending — exactly the kind of position where unguarded null-move pruning misplays zugzwang. The "only king +
  pawns" guard is not optional; skip it and expect null-move to actively cost games it would otherwise win in
  exactly this type of ending.
- **5s/move budget with new recursive paths.** Every new recursive call added (null-move probe, deeper PVS
  re-search, extended-depth negamax on checks) must still hit the existing `self.nodes & 2047 == 0` deadline
  check (`main.rs:82`/`121`) — it's node-count-based so it stays correct regardless of call depth, but a check
  extension that is *not* capped per line (only capped by the global `MAX_PLY = 96`, `main.rs:16`) could burn
  the whole 5s budget chasing one forcing line at low iterative-deepening depth while other root moves get zero
  search at that depth. Cap extensions per line (e.g. max 2), independent of the existing ply/depth machinery.
- **TT correctness vs. the just-added repetition/50-move detection (v3).** A TT entry stored for a position
  reached one way might be probed again when the *path* to it makes it a repetition or near-fifty-move draw
  this time — trusting a stored non-draw score in that context returns a wrong result. Don't cache (or don't
  trust on probe) scores computed within a few plies of `pos.halfmoves()` approaching 100, and always run the
  existing `is_repetition`/50-move check (`main.rs:95`) *before* trusting a TT hit, not after. Also clear the
  table on `ucinewgame` (`main.rs:249-252`) — stale cross-game entries are a subtle, hard-to-reproduce bug
  source.
- **UCI `score mate N` (item 5) is cosmetic risk-free today** — confirmed by reading `arena/evalgame.py:34,40`,
  which already calls `.score(mate_score=10_000)` on `python-chess`'s parsed score object, so both a raw huge
  `cp` value (today) and a proper `mate N` (after item 5) resolve to sane, comparable numbers. No arena change
  needed, just add it for any future non-arena UCI consumer.
